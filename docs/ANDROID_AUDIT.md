### SCREEN TIME ROOT CAUSE & ANALYSIS

**File:** [`DeviceUsageCollector.kt`](file:///c:/Users/tnjok/.gemini/antigravity-ide/scratch/sih_mining/behavioral_well/android/app/src/main/java/ai/behavioralwell/app/data/collectors/DeviceUsageCollector.kt)

The collector first calculates bounded foreground duration using usage events (`queryEvents`) and clamps session intervals against:
- `startTime` (local device midnight 00:00:00)
- `endTime` (`System.currentTimeMillis()`)

However, it subsequently queried:
```kotlin
queryUsageStats(
    UsageStatsManager.INTERVAL_DAILY,
    startTime,
    endTime
)
```
and **unconditionally replaced** the event-derived value:
```kotlin
totalForegroundMs = statsSumMs
```
whenever `statsSumMs > 0`.

This meant the bounded event-derived calculation was completely discarded whenever `queryUsageStats` returned a positive value. System `queryUsageStats(INTERVAL_DAILY)` aggregates multi-day rolling bucket boundaries on OEMs (e.g. realme / ColorOS / MIUI), causing severe multi-day history inflation.

The resulting screen-time value was therefore vulnerable to bucket-boundary/history inflation and exceeded the physically possible active interval for the requested today window (`9.76h` vs physical elapsed time).

#### REQUIRED FIX IMPLEMENTED
1. **Removed the unconditional `queryUsageStats` overwrite.**
2. **Prioritized the bounded event-derived foreground interval calculation** clipped strictly to `[startTime, endTime]`.
3. **Clipped maximum foreground time to `(endTime - startTime)`.**
4. **Reconciled `queryUsageStats` as a secondary DEBUG diagnostic log only**, printing both metrics for diagnostic auditing without overwriting.

### UNLOCK ROOT CAUSE & ANALYSIS

**File:** [`DeviceUsageCollector.kt`](file:///c:/Users/tnjok/.gemini/antigravity-ide/scratch/sih_mining/behavioral_well/android/app/src/main/java/ai/behavioralwell/app/data/collectors/DeviceUsageCollector.kt)

The original implementation contained incorrect assumptions about `UsageEvents.Event` constants, interpreting event values as:
- `17 = KEYGUARD_DISMISSED`
- `18 = KEYGUARD_GOING_AWAY`
- `23 = USER_PRESENT`

In Android's raw `UsageEvents` stream, `15 = SCREEN_INTERACTIVE`, `16 = SCREEN_NON_INTERACTIVE`, `14 = KEYGUARD_SHOWN`, `17 = KEYGUARD_DISMISSED`, `18 = KEYGUARD_GOING_AWAY`.

Counting `SCREEN_INTERACTIVE` or multi-event transitions per unlock cycle caused screen-wake transitions (e.g. ambient display, notification wake, volume rocker press) to be falsely counted as user unlocks, yielding **35 unlocks vs 25 reference unlocks**.

#### REQUIRED FIX IMPLEMENTED
Implemented unlock detection around the actual keyguard state transition:

```text
LOCKED
   ↓
KEYGUARD_HIDDEN (17 / 18 / 23)
   ↓
ONE UNLOCK INCREMENT

UNLOCKED
   ↓
KEYGUARD_SHOWN (14) / SCREEN_OFF (16)
   ↓
LOCKED
```

- **Do NOT count `SCREEN_INTERACTIVE` (15)** as an unlock by itself.
- **Do NOT count `SCREEN_NON_INTERACTIVE` (16)** as an unlock.
- **Do NOT count multiple events generated by one physical unlock** as multiple unlocks.
